# Supervisor Orchestration

監督エージェントの役割は **振り分け・検証・統合** の 3 つ。重い思考は必要時に思考専門エージェントへ委任し、
監督自身は交通整理と品質保証に集中する。

## 基本原則

1. **思考と実行の分離**: 実行係に「考えろ」を要求しない。分析・設計・評価は思考係へ。手順に沿う作業は実行係へ。
2. **監督は軽量に保つ**: 監督がボトルネック化したら委任する。能力ティアを仕事に合わせる。
3. **実行中の指示**: 通常の追加作業は結果が返ってから渡す。利用者の停止・取消・範囲変更は待たずに反映する。継続は同一セッション再開を使う。
4. **証拠校正**: サブエージェントの要約は「主張」であり「証拠」ではない。成果物ファイル・コマンド出力・diff を直接確認する。
5. **単一目的・単一責任**: 同一目的に重複エージェントを立てない。失敗時は目的を絞って再投入する。

## ルーティング: 「手順書がある仕事か？」

| レベル | 認知活動 | 例 | 振り分け先 |
| :--- | :--- | :--- | :--- |
| L1 Remember | 検索・列挙 | ファイル探し、grep | explore |
| L2 Understand | 要約・説明 | 「このコードを説明」 | explore |
| L3 Apply | 手順に沿って作る | 規約に沿った修正、テスト追加 | general（実行係） |
| L4 Analyze | 構造調査・原因究明 | 「なぜこのバグが起きた？」 | 思考係 or 監督 |
| L5 Evaluate | 比較・判断 | 「A と B どちらが妥当？」 | 思考係 + 監督が裁定 |
| L6 Create | 設計・新規作成 | アーキテクチャ設計 | 思考係、統合は監督 |

詳細例は [references/bloom-routing.md](references/bloom-routing.md)。

## ブリーフィング必須項目（委任時に必ず書く）

1. 目的（1 文）と役割（実行係/思考係）
2. 成果物のファイルパスまたは本文の返信先と、完了条件。読取り専用のワーカーにはファイル作成を要求しない
3. 証拠要件（使ったコマンド、引用、確認結果を成果物に含める）
4. 禁止事項（commit/push、スコープ外変更、PII の持ち出し、外部 API へのデータ送信）
5. 返信形式: findings / tips / struggles + 根拠 + 残リスク + 成果物パスまたは本文の参照。要約は25行以内とし、長い本文は別に返す
6. 検証可能であること: 監督が再実行・再読できる形で報告する
7. 複数のワーカー（例: 3体以上）に同じ前提を渡すときは、全員が同じ版を読める場合に共通部分を `brief_common.md` にまとめる。
   対象の版・読取り専用のパス・環境上の注意・禁止事項・証拠要件・返信形式を書き、作業中は内容を固定する。
   各ブリーフには読むファイルの場所と、固有の目的・作業・成果物の出し方を書く。共有できなければ共通部分を各ブリーフに含める。
   これは指示の重複を減らす運用上の選択であり、文字数・token数・品質の改善率は別途測定しない限り主張しない。

## 応答が届かないとき

- 作業の所要時間に応じた確認間隔を決め、実行基盤が提供する状態照会・受信機能で、担当ワーカーの状態と未読の応答を確認する。
  ファイルの更新時刻だけで停止とは判断しない。待機中でも結果が未受領なら返信を依頼し、実行中なら重複した作業指示を送らない。
  状態を確認する機能がなければ確認不能と記録し、停止したと推測して再起動しない。
- ユーザーの割り込み後は最新の指示を確認し、停止・取消なら再開しない。続行が許可されている範囲で、担当ワーカーの状態を確認する。
  中断は失敗と区別して記録する。再実行前に旧ワーカーが動いていないことと既存成果物・副作用を確認し、重複実行を防ぐ。
- 分析系の読取り専用ワーカーには、本文をテキストで返すよう最初から指示する。要約25行とは別に、本文は1通6000字以内を目安とし、
  実行基盤の上限が小さければそれに合わせる。分割時は `(1/3)` のように通数を示し、監督が全通を受領してから必要に応じてファイル化する。

## 検証プロトコル（報告を受けたら）

1. ファイルなら存在・サイズを確認（`ls -la` / `wc -l`）。本文で受け取った場合は分割分の欠落がないか確認する
2. 主要主張を 1〜2 点スポットチェック（コマンド再実行、引用元の実在確認）
3. 要約と成果物の不一致、根拠のない断言、丸写し要約を探す
4. 検証できない主張は「未検証」と明記して統合する
5. 並列結果は対立点を洗い出してから1本に統合する。「できない」と「前提を置けばできる」は前提と主張の範囲を照合し、同じ結論としてまとめない。
   否定の結論には試した条件と確認範囲を付け、「調べた範囲では成立しない」を一般的な不可能性へ広げない。未確認の条件は残す。
   複数の項目を判定するときは、値か区分か、前提つきを認めるかなど、同じ判定基準を使ったか確認する
6. 改善ラウンド後は**旧表現の横断 grep**（例: 陳腐化した語）で残存を潰す

## 成長プロトコル

- セッション終わりに [references/growth-log.md](references/growth-log.md) へ日付付きで追記: 状況 / 学び / 適用した変更。
- 同種の学びが 3 件たまったら SKILL.md に昇格（重複排除し短く）。
- ルールは検証可能な行動で書く（「気をつける」ではなく「〜を確認する」）。

## 境界・安全

- ユーザー可視の Herdr ペインで OpenCode ワーカーを統括する場合は、`herdr-opencode-agmsg`（同梱されていれば）の roster・ACK/READY・provider 切替・owned tab 終了条件を併用する。
- push は明示指示時のみ（commit は依頼時のみ）。
- 会話ログ・PII は作業用の一時ディレクトリのみ、コミットしない。
- 外部 LLM API へ会話・作業データを送る場合は ZDR（Zero Data Retention）を必須にし、保証できなければ送信しない。
- 委任範囲を超える操作（本番環境、破壊的変更、課金）をエージェントに許可しない。
