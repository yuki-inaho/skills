# ONBOARDING.md を書く

新規エージェントが過去の会話を参照せずに、作業対象と現在の状態を特定し、次の作業に着手できる Markdown を作る。既定は対象リポジトリの `docs/ONBOARDING.md` と日本語。既存のオンボーディング文書や利用者の指定があれば、その配置と言語に合わせる。[オンボーディング用テンプレート](references/onboarding-template.md)を読み、項目と粒度を対象に合わせる。環境構築を伴わない資料レビューや成果物アーカイブの引き継ぎにも使える。

## 書く前に確認する順序

1. **対象と基準の版を確定する。** 指定パスと適用される `AGENTS.md` などを読む。Git があればルート、ブランチ、HEAD、作業ツリーの変更を確認する。複数のリポジトリ、サブモジュール、アーカイブが関係する場合は、それぞれの版と役割を記録する。アーカイブだけの場合はファイル名と入手可能な版またはハッシュで特定する。

   ```bash
   git rev-parse --show-toplevel
   git status --short --branch
   git log -1 --format='%h %s'
   ```

2. **目的と読む順序を組み立てる。** `README.md`、既存の `ONBOARDING.md`、関連する作業計画・決定記録・検証結果を読み、現在の目的、完了条件、適用範囲を確かめる。各資料に「何を知るためにどの章を読むか」を付ける。資料と実装の版や内容に差があれば、両方の根拠と差が影響する手順を記す。
3. **成果物と実装を照合する。** 入力、実行入口、設定、出力、検証記録をたどる。対象の生成物・レポート・データ・モデル・配布物について、期待する場所と実際の所在、作成元、参照する検証結果を押さえる。Git 管理外や外部配布の場合は、権限を含む取得方法と取得後の置き場を明記する。更新日時だけで正本や最新版を決めず、生成物の版と対象コードの版の関係を確認する。不明なら影響と確認方法を書く。
4. **実行手順を現物から組み立てる。** マニフェスト、ロックファイル、タスク定義、CI、実行入口を照合する。必要な OS・ツール・権限・入力と、既存環境を再利用できる判定を示す。作業ディレクトリ、コマンド、成功条件、出力先を明示し、設定・秘密情報は変数名と取得先で説明する。環境別の分岐は成果物の確認や作業再開に関係するものに絞る。
5. **確認済みの範囲を記録する。** 先に読み取りだけで現状を確かめる。依頼範囲と利用できる環境に応じて、既存の軽い確認コマンドで起動、サンプル実行、検証記録の照合などを行う。結果は実行した版・入力・主要出力とセットで記し、過去の実行結果や手順から分かったことと区別する。再生成の手順を書く場合は既存成果物の置き場を確認し、可能なら別の出力先を使う。

## 文書にまとめる

- 冒頭に対象、確認日、基準の版、引き継ぎの目的、着手時の読み順を置く。長い場合は目次を付ける。
- 構成の説明から各コンポーネントのドキュメント、コード、生成物にたどれるようにする。リポジトリ内は相対リンクを使い、必要なら見出しやレコード名を併記する。外部の資料も名前、用途、所在を示す。
- 状態表には対象、状態、根拠、必要なら次の確認を置く。今回現物を確認した範囲、既存の記録が示す範囲、未確認、必要な入力が足りず実行できない状態を言葉で区別する。ファイルの実在、生成の成功、内容の妥当性を同じ確認結果として扱わない。
- 既存環境の確認後、必要な場合に限ってセットアップする流れにする。再開時のコマンドと期待結果を対にし、生成物を確認するだけで足りる場合の終点も示す。
- トラブル対処は観測できる症状、切り分け方、復帰後の確認を書く。次の作業には順序、前提、完了を判断できる条件を付ける。実行しなかった検証も追跡できるよう、理由と次回使う入口を示す。
- 既存の文書を更新する場合は、形骸化した例や古い経路を必要な範囲で直し、引き続き有効な決定と検証記録を残す。

## 仕上げ

1. 冒頭の確認順に沿って、文書から根拠、実行入口、成果物の場所にたどれることを確かめる。コマンドの作業ディレクトリ、リンク先、目次のアンカー、必要な入力と期待結果が実体に合うか確認する。
2. テンプレートの例や記入欄を実情報へ置き換え、確認できない事項には理由と確認方法を付ける。動作を確認した版と未実行の確認が読み手に伝わるよう見直す。
3. 作成・更新した文書のパスと、確認した内容、再開に影響する未確認事項を利用者へ伝える。
