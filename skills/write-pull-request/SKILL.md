# Write Pull Request

PRの読み手が「何が変わるか、何を確かめたか、何がまだ分からないか」を、現行の差分から判断できる本文にする。

## When to use

PRの新規作成、既存PRの本文修正、またはその下書きに使う。コードレビューやmerge判断を代行しない。

## Prerequisites

- 対象リポジトリ、base、head、既存PRの有無を確認する。既存PRを直すときは現行本文も読む。
- 最新の差分、関連Issue、テスト結果、CI、実機・本番確認の記録を区別して集める。取得できない資料は「確認した」と書かない。
- 公開PRでは、本文・リンク・添付に内部情報を持ち込まない。公開前のプライバシー点検が必要な場合は、利用環境の方針に従う。

## Procedure

1. baseとの差分とPRの現在の状態を読む。`gh`が使える環境なら、次を入口にできる。別のGit連携でも同じ情報を確認すればよい。

   ```bash
   git status --short
   git diff --stat origin/main...HEAD
   git diff origin/main...HEAD
   gh pr view --json title,body,state,isDraft,url
   ```

   `origin/main`は実際のbaseに置き換える。既存PRを直す場合、merge後の差分だけで過去の変更内容を推測しない。

2. 先に事実を整理する: 元の問題、実際に変えたもの、確認した範囲、未確認・既知の失敗、利用時に必要な操作。数値、commit、イメージ、日時には出所を付ける。子リポジトリ単体の結果を親アプリ全体の結果と言い換えない。ローカル試験、CI、実機試験も混同しない。
3. リポジトリ内のPRの書き方に合わせ、必要な見出しだけを使う。典型例は「背景」「変更」「確認」「未確認・利用時の注意」。原因を別に説明する必要がなければ「原因」節は作らない。比較が必要な参照先だけ表にし、実行順や理由は文章で書く。
4. 変更が必要な理由から書き始める。抽象的な成果や未定義の造語で要約しない。確認欄には成功だけでなく、失敗・制約・対象外も残す。将来形の「確認します」は、実施済みなら結果と証跡に直す。後日得た結果は、元のPR時点の結果と時系列を分けて記す。
5. 読み手の判断に必要な場合だけ、再ビルド、設定変更、互換性、戻し方を書く。ソースだけのタグを配布済みイメージと呼ばない。直接の根拠へリンクし、長い実行ログは本文に複製しない。
6. 投稿や更新を依頼されている場合のみ、利用可能なGitHub連携で反映する。本文だけを直すために無関係なソースをcommitしない。反映後はPRを再取得し、タイトル・本文・Draft状態が意図どおりか確認する。mergeやdeployは別の操作とする。

## Verification

- 本文の主要な主張が、差分または引用した試験結果に対応する。
- 数字・対象範囲・失敗・未確認事項が残り、既存本文の正しい情報を誤って消していない。
- 現在のPR状態に合わせて時制を更新し、過去の時点の事実にはその時点を明記した。
- リモートを更新した場合は、再取得した本文と意図した原稿が一致する。

## Failure handling

- baseや試験結果が不明: 推測で補わず、その部分を未確認と書くか、確認可能な事実だけで下書きを作る。
- CIや実機記録が後から増えた: 既存の結果を上書きせず、どの時点・対象の試験かを分けて追記する。
- 投稿権限や接続がない: 原稿まで作り、未反映であることを明記する。別経路で勝手に公開しない。

## Growth log

実際のPRで同じ誤読が繰り返された場合にだけ、この手順へ一般化して反映する。個別PRの番号や結果は持ち込まない。
