# Write Issue

読み手が、どの記述や動作に問題があり、何が根拠で、どこを直せばよいか判断できるIssue本文を書く。

## When to use

不具合や、仕様・説明・テストと実際の動作の不一致を報告するときに使う。チャットでの文案作成と、既存Issueの本文修正にも使える。調査や文案作成だけの依頼から、投稿や実装修正へ進まない。

## Prerequisites

- 対象と操作を特定する。文案の提示、下書きの保存、既存本文の編集、コメント追加、状態変更は別の操作として扱う。会話で決まった目的・文面・範囲を優先し、既にある許可を聞き直さない。
- 既存Issueを直す場合は、現在の本文と状態を読む。新規投稿を依頼された場合は関連Issueと重複の有無、リポジトリのテンプレートを調べる。優先度・ラベル・担当者は利用者の指定やリポジトリの運用に合わせ、文章修正のついでに変更しない。
- 根拠となる記述・実装・実行結果を集める。取得できない資料や他エージェントの報告は、自分で読んだ・実行したものと区別する。

## Procedure

1. **報告の目的を保つ。** 不一致の報告と修正依頼なら、読み手に説明を求める質問へ変えない。「指摘が妥当であれば、対象の説明とテストを修正してください」のように、対応する条件と対象を書く。質問を依頼されている場合は、質問のまま扱う。
2. **元の主張と観測を照合する。** 対象版・入力条件・期待される結果・実際の結果を揃える。実装の不具合、説明の不整合、テストの不足、意図的な変更を区別し、観測が支える範囲で結論を書く。エージェント同士が同意したことを、コードや実行結果の代わりの根拠にしない。
3. **冒頭で問題と対応をつなぐ。** 何が食い違い、どの判断や動作に影響するかを短く書く。複数件なら「元の記述・期待する動作｜実際の結果｜問題｜修正案」の表を使える。原文の該当箇所と再現結果へのリンクを、それぞれのセルに置く。表の形を固定せず、一件なら文章で済ませてもよい。
4. **その根拠を直接辿れるようにする。** 文書の節、コメント、コード行など、主張を支える箇所へリンクする。版に依存する指摘はcommit等で参照を固定する。関連Issueの入口だけを根拠にせず、各リンクが隣の主張を実際に支えているか読む。
5. **最小の再現手順を添える。** 必要な版・依存環境・入力・コマンド・期待結果を揃え、第三者が取得できるファイルを使う。リポジトリ相対パスを使い、作成者だけのスキルや絶対パスを前提にしない。共有済みスキルを使う場合は、その参照先と必要な手順を示す。順序を制御した実験、実環境での観測、コード読解は、同じ検証と呼ばない。
6. **判断に必要な情報を残す。** 結論の適用範囲や再現に関わる制約は短く明記する。途中の試行・全ログ・担当の履歴は本文に積み上げず、必要な記録だけリンクする。修正案が未実装なら、直った結果として書かない。
7. **依頼された場所へ反映する。** 文案だけなら指定された場所へ出す。投稿・更新が依頼済みならその範囲で進め、既存本文の修正を追加コメントで代用しない。下書きを求められた場合は対象サービスの下書き機能を確かめ、利用できなければ原稿を保持して制約を伝える。通常のIssue作成やCloseで代用しない。

   `gh`で既存本文を更新する例。プレースホルダは実際の対象に置き換え、更新コマンドは本文編集が依頼されている場合に使う。

   ```bash
   gh issue view <number> --repo <owner/repo> \
     --json title,body,state,labels,assignees,milestone,url
   gh issue edit <number> --repo <owner/repo> --body-file <body-file>
   ```

   更新直前に現行本文との差分を見て、他者の追記を上書きしない。本文の更新以外に必要な操作があれば、既存の指示がその操作まで含むか確かめる。

## Verification

- 冒頭から、元の主張・実際の結果・問題・必要な対応が分かり、それぞれの根拠へ辿れる。
- 再現手順の参照先が共有されており、実行済みの結果と他者の報告・推測を混ぜていない。
- 反映後に本文を再取得し、原稿と一致することを確かめる。語句だけでなく、依頼された問題が文章全体で直ったか読む。
- 更新対象、状態、コメントの追加などが許可された範囲に収まっている。文案のみなら未投稿であることを明記する。

## Failure handling

- 再現しない・根拠が不足する: 事実と仮説を分け、断定を弱める。合意済みの結論に合わせて測定条件を変えない。
- 最新版では挙動が変わった: 再現した版と現在の版を分け、過去の結果を現状の不具合として断定しない。
- 投稿や編集が失敗した: 原稿を保持し、未反映と伝える。重複作成や別の投稿先で代用しない。
- 読者が根拠を開けない: 許可された範囲で共有可能な再現材料を揃える。私的なログや認証情報を本文へ貼らない。

## Growth log

繰り返し起きた誤読や操作の取り違えだけを、案件固有の識別子・会話・結論を除いて手順へ反映する。特定の指摘に同意することを、スキルの合格条件にしない。
