# write-workdoc-uv template reference

Use this reference as the base template when creating a workdoc. Preserve the structure closely, but fill placeholders with concrete task-specific information. Insert the goal requirement analysis section directly under `## 1. 作業目的`.

---

% 命令

`workdoc_{ローマ字3字でdateで調べた月を表現。Aprとか}{日付}-{西暦}_*.md` という名前フォーマットのマークダウンドキュメントで `temp/` 以下に、誰が見ても文脈がわかり、迷わず作業ができるほど具体性高い形で以下の作業書を作成してください。

長くなっても良いのでとにかく詳細に・具体的に・明示的に。以下のテンプレートには忠実に。計画・調査・実装のフェーズを混同しないこと。他エージェントが作業を行うので self-consistent, self-contained, well-defined な形でステップを細かく踏みつつ作業内容を考えること。

他エージェントが読んでも文脈が self-consistent, self-contained, well-defined にわかるような形で、長くなっても良いから詳細に記述してください。また、ユーザーの直観的・直截的な目的に紐づく形でゴール要求分析を行い、サブゴール構造を分析し、目的欄の下にその分析結果の章を作ってください。また、その分析結果に紐付いた形で作業要素を定める形としてください。また、監査エージェント的にトレーサビリティが取れることを意識しながら作業すること。

**命令**

チェックリストを、**「誰が実行しても迷わない最小単位のアクション」** に分割してください。

分割にあたっては次のルールを厳守してください。

1. **原子性** - 各ステップは一度に一操作。完了判定が明確であること。
2. **順序性** - 依存関係がある場合は必ず前後関係を保持すること。
3. **検証可能性** - 各ステップに「完了確認方法（期待結果）」を必ず付記すること。
4. **テスト駆動（TDD）要素 (可能であれば)** -
   - 各ステップ開始前に対応するテストケースを記述すること。
   - ステップ完了後、そのテストが**失敗→成功**に変わることを示すこと。
5. **エラー時の指針** - 想定されるエラーと代表的な対処法を追記すること。
6. **表記形式** - 以下のMarkdown形式を厳守してください。

```markdown
### 手順 n: <目的を端的に>
- [ ] 🖐 **操作**: <コマンド／編集内容など>
- [ ] 🔎 **確認**: <期待結果>
- [ ] 🧪 **テスト**: <テストケース名／初期失敗・後成功の確認方法>
- [ ] 🛠 **エラー時対処**: <代表的なエラーと解決策>
```

## 注意点

- uv環境で作業を行うこと。
- 必要であればjustfileを用いながら作業を行うこと。
- DRY/KISS/SOLID原則やt-wada TDDを遵守した再利用性・可読性の良い・記述の冗長性の少ないコード作成を念頭においてください。
- 暗黙的なfall backは許容できない。
- 他エージェントが監査を行うので、結果のトレーサビリティが取れるような形を念頭において作業を行うこと。

% 補助情報

**このテンプレートの使い方**

このドキュメントは、日々の作業計画と実績を記録するためのものです。以下の各セクションを埋めて使用してください。計画を立て、実績を記録することで、作業の振り返りやチームへの情報共有が円滑になります。

また、作業記録の上での注意事項部分は書き換え後も残るようなかたちにしてください。

## 2. 作業内容

### フェーズ 1: [調査・設計フェーズ] (見積: [X.X]h)

このフェーズでは、実装に着手する前の準備作業を行います。

1.  **現状のアーキテクチャ分析：**
    *   **タスク内容：** `[対象のソースコードやモジュール名]` を精査し、現在の設計や実装の詳細を把握します。
    *   **目的：** 変更が必要な箇所と影響範囲を正確に特定し、安全な作業計画を立案します。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
2.  **依存コンポーネントの確認：**
    *   **タスク内容：** `[関連するライブラリやクラス名]` など、変更対象が依存するコンポーネントの仕様を確認します。
    *   **目的：** 依存関係を理解し、手戻りのない設計を行います。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
3.  **設計方針の文書化：**
    *   **タスク内容：** 分析結果を基に、具体的な実装方針やクラス設計などをまとめます。
    *   **目的：** 実装のロードマップを明確にし、作業中のミスや見落としを防ぎます。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`

### フェーズ 2: [メイン機能の実装] (見積: [X.X]h)

このフェーズでは、設計方針に基づいて主要な機能を実装します。

1.  **[実装タスク1]：**
    *   **タスク内容：** `[クラス名]` に `[新しいメソッド名]` を追加し、`[具体的な処理内容]` を実装します。
    *   **目的：** `[そのタスクで実現したいこと]` を実現します。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
2.  **[実装タスク2]：**
    *   **タスク内容：** `[設定ファイル名]` に新しいパラメータ `[パラメータ名]` を追加し、それを読み込む処理を実装します。
    *   **目的：** システムの動作を外部から柔軟に制御できるようにします。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
3.  **[実装タスク3]：**
    *   **タスク内容：** `[既存の関数名]` をリファクタリングし、処理を効率化・可読性を向上させます。
    *   **目的：** 技術的負債を解消し、将来のメンテナンス性を向上させます。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`

### フェーズ 3: [テストと動作検証] (見積: [X.X]h)

最終フェーズでは、実装した機能が意図通りに動作するかを総合的にテストします。

1.  **単体テストの作成と実行：**
    *   **タスク内容：** `[テストフレームワーク名]` を使用して、フェーズ2で実装した機能の単体テストを作成し、実行します。
    *   **目的：** 個々の機能が単独で正しく動作することを保証します。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
2.  **結合テストの実施：**
    *   **タスク内容：** `[ビルドツールやスクリプト名]` を使ってシステム全体を起動し、機能間の連携が正しく行われるかを確認します。
    *   **目的：** 既存機能への悪影響（リグレッション）がないことを確認します。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`
3.  **品質チェック：**
    *   **タスク内容：** コードフォーマッタ（例: `black`, `prettier`）とリンター（例: `flake8`, `eslint`）を実行し、コード品質を担保します。
    *   **目的：** コード規約を遵守し、チーム全体の開発効率を維持します。
    *   **対応サブゴール/Trace ID：** `[SG-x / TR-x]`

## 4. 作業に使用するコマンド参考情報

### 基本的な開発ワークフロー

```bash
# 依存関係の同期
uv sync

# justfileが存在する場合のタスク一覧
just --list

# 全体のビルドまたはプロジェクト固有チェック
[ビルドツールまたはjustターゲット] build

# 開発環境の起動
docker compose up -d

# 開発環境の停止
docker compose down
```

### テストと品質管理

```bash
# 全テストの実行
uv run pytest

# 対象テストのみ実行
uv run pytest [テストファイルまたはテスト名] -q

# コードフォーマット
uv run ruff format .

# リンターチェック
uv run ruff check .

# 型チェック例
uv run mypy [対象パッケージ]
```

### 特定機能の実行・デバッグ例

```bash
# [特定のノードやアプリ]を[パラメータ付きで]起動する
uv run [実行モジュールまたはスクリプト] --config [設定ファイルパス] --param [値]

# サービスの動作確認
[ツール名] service list | grep [キーワード]

# API呼び出しテスト
curl -X POST http://localhost:8000/[エンドポイント] -d '{...}'
```

## 7. 作業記録

**重要な注意事項：**

*   作業開始前に必ず `date "+%Y-%m-%d %H:%M:%S %Z%z"` コマンドで現在時刻を確認し、正確な日時を記録します。
*   各作業項目を開始する際と完了する際の両方で記録を行うこと。
*   作業内容は具体的なコマンドや操作手順を詳細に記載すること。
*   結果・備考欄には成功／失敗、エラー内容、解決方法、重要な気づきを必ず記入すること。
*   複数のフェーズがある場合は、フェーズごとに開始・完了の記録を取ること。
*   コード変更を行った場合は、変更したファイル名と変更内容の概要を記録すること。
*   エラーが発生した場合は、エラーメッセージと解決策を詳細に記録すること。
