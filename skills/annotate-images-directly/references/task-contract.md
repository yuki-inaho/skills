# 案件契約と補助入出力

## 作業前に案件側で固定する情報

| 項目 | 固定する内容 |
| --- | --- |
| 対象 | 元の対象定義、カテゴリ、含める例・除外する例、判別不能の扱い |
| 可視性 | 可視部分のみか全体推定か、遮蔽で分離した部分、画面端で欠けた部分の扱い |
| 点 | 内点、中心、特徴点などの役割。境界上を認めるか |
| 形 | BBOXとポリゴンが表す領域、離れた可視領域を別 object にする条件 |
| 座標 | 原画像の向きと寸法、原点・軸方向・単位・上下限、整数化、画像端か画素中心か |
| 出力 | 正本の形式、カテゴリ制約、領域数・頂点数上限、検査コマンド |
| 採点 | 正本の採点器、参照形式、塗り潰し・丸め・重なりの処理、分母・画像間集約、空集合の扱い |
| 記録 | 注釈開始前に固定した入力・設定・手順・補助コード・例題の版とハッシュ、予定回答ID、実行時に観測できるモデル・設定、保存先 |

既存の定義・形式・上限・検査器・採点器がある場合はその内容を保持します。たとえば全画像の共通部分と和集合を積算する指標を、画像ごとの率の平均へ変更しません。補助警告だけを理由に公式の不正判定や対象除外へ変更しません。

外見が似ていても、装着先・用途・所属などの関係によって対象が決まる場合があります。対象候補について、その関係を画像から確認できたかを短く記録し、根拠不足を輪郭の精密化で補ったことにしません。色付き例題を使う場合は色とクラスの対応を明示した凡例も固定し、不明な対応は推定または不明として残します。試行途中の手順・補助コード・例題の変更は、元の版を上書きせず別条件として扱います。

## 注釈担当へ渡す入力

案件側で明示した許可リストから、評価対象画像１枚と、その画像の解釈に必要な契約・形式を取り出します。利用者が明示的に認めた別の例題は、契約で版を固定したうえで追加できます。例題の使用有無・ID・版を記録し、例題なしの試行と比較条件を混ぜません。元の manifest に参照者の note が含まれる場合も、その manifest 全体を渡しません。評価対象の参照答案・参照ラベル画像・期待個数・採点結果、同じ評価組の他画像の回答、評価画像の答えを復元できる生成コードを除きます。

独立した担当を起動する場合は画像ごとに新しい推論入力を作ります。担当への指示だけではファイルへのアクセス権を制限できない環境もあるため、実際に渡したファイルと情報、隔離できなかった範囲を記録します。参照を見る前の検討と、参照を見た後の修正を同じ独立試行として扱いません。

## 幾何補助の形式

`annotation_run.py` は対象名を解釈せず、`objects` 配列または最上位配列の各要素から `point`、`bbox`、`polygon` を読みます。各要素に少なくとも１種類必要です。３種類がそろう場合は同じ領域に対応するものとして、BBOXによる点・輪郭の包含を検査します。カテゴリ、追加項目、整数制約、領域数・頂点数上限は案件側の検査器で確認します。

以下は架空の図形を表す合成例です。

```json
{
  "image_id": "sample-01",
  "objects": [
    {
      "class": "shape",
      "point": {"x": 24, "y": 20},
      "bbox": {"xmin": 8, "ymin": 8, "xmax": 40, "ymax": 32},
      "polygon": [{"x": 8, "y": 8}, {"x": 40, "y": 8}, {"x": 40, "y": 32}, {"x": 8, "y": 32}]
    }
  ],
  "review_needed": false
}
```

点・頂点は `[x, y]`、BBOXは `[xmin, ymin, xmax, ymax]` でも読み取れます。ポリゴンの末尾へ先頭頂点を重複して追加しません。別の形式を使う案件では、対応を明記して検査用データへ変換します。検査用データを正本の提出形式へ置き換えません。

`--point-location inside` は厳密な内部、`covered` は境界を含む内部を要求します。既定の `any` は点とポリゴンの位置関係を検査しません。点の意味に応じて選びます。

幾何エラーは非有限値、真偽値の座標、範囲外、逆転・退化BBOX、頂点不足、重複頂点、面積ゼロ、自己交差・自己接触、隣接辺の折返し、対応する点・輪郭のBBOX外への逸脱です。頂点上限やカテゴリ集合をここで別途定義しません。

警告は、ポリゴンの外接矩形に対するBBOX余白、同じ領域、領域の接触・重なり、整数画素へ丸めた頂点の重複・面積消失です。接触と正の面積の重なりは厳密に区別せず、目視の確認候補として報告します。警告では回答を変更せず、終了コードも失敗にしません。

## 原画像上での表示

`overlay` はPNG・JPEG・GIFを元のバイト列のままSVGへ埋め込みます。幅・高さは画像ヘッダーと照合しますが、完全な画像復号やEXIFの向き補正はしません。先に向きが確定した原画像を用意します。画像上限の位置は明示的に選びます。

- `pixel-centers`: 幅 `W`、座標上限 `M` に対して画素添字は `x * (W - 1) / M`。SVG内の画素中心はその値に `0.5` を足した位置です。
- `image-edges`: SVG内の画像端を `0` と `W` とし、位置は `x * W / M` です。

y方向も高さに対して同じ変換を使います。補助の画素退化確認は上記の画素座標をPythonの `round` で整数へ丸める診断です。公式採点の丸め・塗り潰し・画素面積の規約を実装するものではありません。規約が異なる場合は公式の描画結果も確認します。ポリゴンが小さいという理由だけで削除しません。

## 全回答の凍結

`freeze` は、案件側で作った以下の小さなファイル一覧を読みます。これは注釈担当へ渡す入力一覧とは別です。各パスはこの一覧ファイルのある場所を基準とします。期待するIDは先に固定し、提出できた回答だけから後で作らないでください。

```json
{
  "run_id": "synthetic-run",
  "expected_answer_ids": ["sample-01", "sample-02"],
  "inputs": {"sample-01": "image-01.png", "sample-02": "image-02.png"},
  "settings": {"contract": "task-contract.json", "validation": "validation-results.json"},
  "answers": {"sample-01": "answers/sample-01.json", "sample-02": null}
}
```

`inputs` と `settings` は空にしません。実行した検査器の結果も `settings` に指定して一緒に確定します。`answers` に予定IDの項目がない場合や値が `null` の場合は `unsubmitted`、指定したファイルがない場合は `missing`、読めない場合は `unreadable`、回答がJSONとして不正なら `invalid_json` を残します。JSON不正でも取得できたバイト列のハッシュは残します。予定外IDや重複したJSONキーは拒否します。

`recorded` はファイルを読み取ってハッシュを得た状態です。回答についての自動確認はJSON構文のみで、案件形式・幾何・意味の妥当性を保証しません。不合格の回答も除外せず、別途確定した検査結果と合わせて報告します。

凍結の出力には元の一覧、入力、設定、全予定回答IDのパス・状態・SHA-256が残ります。標準出力に出る凍結ファイル自体の `sha256` は別の実行記録へ保持し、`verify` に渡します。検証時に再計算した値へ置き換えると、凍結ファイル自体の改変を検出できません。

`verify` は凍結ファイルの変更、記録したファイルの変更・削除、当初存在しなかった指定先へのファイルの追加を拒否します。未提出の `null` にはパスがないため、保存先を探して新しい回答を推測しません。元の一覧を変えればその変更を検出します。これは完全なアクセス制御や第三者による時刻証明ではなく、保持したハッシュに対する内容確認です。

終了コードは0がエラーなし、1が幾何エラー・不完全な凍結・確定後の不一致、2が入力の読取り・コマンド指定・出力作成などの異常です。既存のSVGや凍結ファイルは上書きしません。参照を見て回答を修正したら別の一覧・回答・凍結ファイルを作ります。
